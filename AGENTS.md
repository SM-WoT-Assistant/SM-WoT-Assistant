# Правила роботи з проектом WoT Assistant

## Критичне правило (СУВОРО, 100-й раз)
1. **НІКОЛИ НІЧОГО НЕ ВИГАДУВАТИ!** Жодних власних інтерпретацій, фантазій, "напевно", "мабуть", "можна припустити". Тільки те, що є в коді, документації та відповідях користувача.
2. Якщо не впевнений — запитай, а не вигадуй.

## Джерела даних (СУВОРО)
1. ВСІ дані беруться ТІЛЬКИ з клієнта гри (WotXmlParser декодування XML) або з відповідей ШІ.
2. НІЯКИХ хардкоджених списків, фалбеків, кешів без прямого дозволу.
3. КОЖНЕ твердження "це з клієнта" має супроводжуватись доказом: файл + рядок коду.

## Role — Think Like a Maintainer
Головна мета — НЕ генерувати код, а **зберігати і покращувати проєкт з мінімальним ризиком**. Кожна зміна має бути: мінімальною, обґрунтованою, підтримуваною, сумісною з існуючою архітектурою. Не переписувати робочий код без явного запиту. Поводитись як технічний лід, а не як генератор коду.

## General Principles
1. **Understand before coding** — спочатку аналіз: прочитати релевантні файли, зрозуміти дані/потоки, залежності, корінь причини; лише потім змінювати код. Ніколи не поспішати одразу генерувати код.
2. **Never guess** — якщо інформації недостатньо або впевненість низька: сказати, пояснити чому, поставити уточнювальні питання. Не вигадувати: класи, методи, API, конфігурацію, схеми даних.
3. **Search before creating** — перед створенням будь-чого (клас, хелпер, віджет, функція, утиліта) шукати існуючу реалізацію в проєкті і перевикористовувати. Не створювати дублікати.
4. **Minimal diff** — змінювати ТІЛЬКИ те, що потрібно: не переписувати нерелевантні модулі, не перейменовувати без причини, не змінювати стиль глобально, не рефакторити робоче без потреби.
5. **Full code** — ніколи не скорочувати код: жодних "...і так далі", "аналогічно", "решту реалізуйте самі". Завжди повністю готовий до використання код.
6. **Preserve architecture & backward compatibility** — не ламати існуючу функціональність; breaking change — спершу пояснити чому, лише потім робити.
7. **Options first (AI Decision Policy)** — кілька варіантів реалізації: коротко переваги/недоліки → рекомендація + чому → лише тоді код. Обирати найбезпечніший варіант; не обирати найшвидший, якщо він знижує підтримуваність.
8. **Quality over speed** — краще більше часу на аналіз, ніж неправильне рішення.
9. **Explain root cause** — пояснювати причину бага, а не лише виправлення; чому саме це виправлення його усуває.
10. **Comments** — коментарі пояснюють "навіщо" і складну логіку; не коментувати очевидне.
11. **Performance** — віддавати перевагу O(n) над O(n²), уникати повторних обчислень і зайвих алокацій.
12. **Safety** — ніколи не хардкодити/логувати секрети; валідувати дані; безпечна робота з файлами; коректна обробка винятків.
13. **Modern alternatives** — можна повідомити про сучасніше рішення і чому воно краще, але пропозиція ≠ дозвіл переписувати робочий код.
14. **No silent deletions** — кожне видалення коду пояснити (підтверджено невикористаним, запит користувача, є заміна).

## Workflow
Перед будь-якою зміною проходити цикл:
`Read → Understand → Search → Plan → Modify → Verify → Explain`
Великі задачі: розбивати на етапи (аналіз → план → ризики → реалізація), вести todos, не генерувати код до узгодження плану.

## Verification (тест-фірст — обов'язково)
1. Перед зміною коду на регресії: статичний аудит (ast-parse без .pyc) + ізольовані smoke-тести — "Спершу подивись щоб нічого не зламати!" (#1471).
2. Після кожної зміни перевіряти: імпорти, ast, рантайм, залежності. Ніколи не припускати, що код працює.
3. Термінальний вивід програми — джерело істини: читати логи самому, не просити користувача вставляти.
4. Для window/overlay/positioning фіксів: debug-print цикл (#1463) — [DEBUG] принти в ключових точках, запуск, порівняння, прибрати лише після підтвердження.
5. Після верифікації не лишати тестових процесів/вікон/файлів.

## Debug Rules
При баг-фіксах: ідентифікувати корінь причини → пояснити → верифікувати гіпотезу → лише тоді імплементувати фікс. Ніколи не патчити наосліп. Трасувати ВЕСЬ конвеєр даних (scrape → parse → validate → display) перед правкою одного файлу (#1387).

## Session Rules
1. Старт сесії: чистий git status; контекст відновлювати з AGENTS.md + релевантних docs/ (НЕ з пам'яті — #1482).
2. Цей файл читається перед кожною дією. Якщо правило порушено — негайно виправити; після виправлення — перевірити результат.
3. Значні зміни документувати негайно: датований запис у docs/changelog.md + оновлення тематичного файлу docs/.
4. Кінець сесії: git add -A && commit.

## Критичні факти (завжди в контексті)
1. **Шляхи**: config.BASE_DIR (бандл), config.USER_DATA_DIR (%APPDATA%/SM WoT Assistant). **НІКОЛИ не чіпати AppData settings.json** (#1219) — всі фікси геометрії тільки кодом.
2. **Версії**: VERSION (головна; config.load_version() додає " Beta"), admin_version.txt (адмінка, незалежна). Зміна адмінки після релізу → бамп admin_version.txt (#1446).
3. **Білд**: `python build.py X.Y.Z` (головна; кожен білд = GitHub release; брудний git блокує), `python build_admin.py` (адмінка, onedir → dist/SM WoT Assistant Admin/, перед перезбіркою вбити запущену адмінку).
4. **Мутекси**: SM_WoT_Assistant_SingleInstance, SM_WoT_Assistant_Admin_SingleInstance, SM_WoT_Assistant_TrayWatcher. Патерн: `WinDLL("kernel32", use_last_error=True)` + `get_last_error() == 183` (#1474).
5. **Мова**: 'uk' (не 'ua'); UI через `app.t('ui', key)`; класи LT/MT/HT/TD/SPG завжди англійською.
6. **Дані**: ТІЛЬКИ з клієнта гри / Firebase / відповідей ШІ (див. Джерела даних).
7. **Overlay**: двовіконна архітектура (#1259); не міксувати pack+grid в одному фреймі (#1327); 6 пунктів overlay startup fix — docs/painter.md.
8. **Трей**: F10; tray wndproc = чистий форвардер, жодного Tk/I-O в колбеку (#1440); PE_SIZE 568/556 (#1309); tray_watcher = stdlib+ctypes без tkinter/PIL/requests.
9. **Кеші**: валідація на load і save (#1346); повний реєстр — docs/cache.md.
10. **RTDB видалення**: PUT null, ніколи `requests.put(json=None)` (#1470).
11. **Release Cleanup Protocol** (після КОЖНОГО релізу): локально dist/ → лишити 5 останніх білдів; GitHub → видалити релізи старші 5 останніх (`gh api -X DELETE releases/{id}`); RTDB versions/ → лишити 5 останніх + latest (PUT null). Повна процедура — docs/release.md.
12. **No dead code**: новий .py без імпортерів (перевірка grep'ом імпортів) — одразу в _archive/scripts/; тестові виводи (html/json/log/txt-дампи) не комітити; розхідники (dist, extracted_gui, temp_scripts.zip) чистити.

## Cross-session пам'ять (Magic Context plugin)
1. Пам'ять автоматично інжектиться в контекст — перевірка на старті НЕ ПОТРІБНА.
2. **Наприкінці сесії:** зберегти ключові факти в `ctx_memory`:
   - над чим працювали (поточне завдання)
   - які баги/проблеми знайдено
   - які рішення прийнято
   - наступний крок
3. **Під час сесії:** зберегти важливі архітектурні рішення, знайдені шляхи файлів, конфігурації, робочі команди негайно після їх виявлення.
4. **magic-context.jsonc** (02.06.2026): налаштовано на максимум — memory.injection_budget_tokens=20000, auto_promote=true, promotion_threshold=2, retrieval_count=1, auto_search score_threshold=0.3, pin_key_files enabled, embedding=local, sidekick enabled, two_pass historian.

## Forbidden
1. Вигадувати/інтерпретувати — жодних "напевно", "мабуть", "можна припустити" (критичне правило).
2. Хардкоджені списки, фалбеки, кеші без прямого дозволу.
3. Змінювати код без необхідності (мінімальний диф).
4. Видаляти код мовчки — пояснити кожне видалення.
5. TODO замість коду, pseudo-code, заглушки.
6. Ігнорувати існуючу архітектуру / порушувати сумісність.
7. Тестові файли/принти/DEBUG в продакшн-шляхах.
8. Shell wildcards для файлів з не-ASCII іменами (#1492).
9. Змінювати без верифікації — тест-фірст обов'язковий (#1471).
10. Пропонувати переписування робочого коду як виконану дію — спочатку запитати.
